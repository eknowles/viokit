# TDR-008 — Schema→form generation: adopt a JSON-Schema renderer vs build one

- **Status:** decided
- **Owner:** ed
- **Date:** 2026-08-23
- **Related:** `openspec/exploration/04-web-ui.md` §4.1; TDR-002 (console stack); TDR-016 (`catalog_describe` publishes JSON Schema); invariants I6

## Decision summary
> Build a small renderer in the console over the Draft-2020-12 documents `catalog_describe` already publishes — primitives, enums, required/optional, descriptions — with a raw-JSON fallback for anything unrenderable and per-transform custom components taking precedence. `@rjsf` deferred until published inputs are routinely nested or conditional.

## Context
- `04-web-ui.md` §4.1 sets the principle: a transform's input form is **generated from its schema**, with custom components as an escape hatch. "A new transform gets a working form the moment it's registered."
- The question is much narrower than when it was first parked. `catalog_describe` already publishes each transform's input and output as **JSON Schema Draft 2020-12**, converted from the Effect Schema that actually decodes the input (TDR-016). So the client is not deriving a form from an Effect AST across a wire — it receives a JSON Schema document.
- **What the schemas actually look like today** is the crux: the registered transform inputs are flat structs of strings and optional numbers. The published documents are correspondingly shallow — `type: "object"`, `properties`, `required`, with primitive leaves and enums for literal unions.
- Constraints: whatever renders the form, the authoritative validation is the engine's boundary decode (I6) — a client-side form is convenience, never the check that matters.
- Affects `apps/console` only.

## Options considered

### Option A — Build a small renderer over the subset we publish
- **Description:** Walk the JSON Schema document; map `string`/`number`/`boolean`/`enum` to inputs, honour `required`, show `description` as help text, and render anything unrecognised as a raw JSON textarea. Per-transform custom components register by id and take precedence (the §4.1 escape hatch).
- **Pros:** No dependency, so no styling to fight and no bundle cost. Covers every schema currently published. The unrecognised-shape fallback means an exotic schema degrades to a usable textarea rather than a broken form. Small enough to read in one sitting.
- **Cons:** We own it. Nested objects, arrays, `oneOf`/`anyOf`, and conditional schemas are not covered — the day a pack ships one, either the fallback carries it or the renderer grows.

### Option B — Adopt `@rjsf` (react-jsonschema-form)
- **Description:** The established React JSON-Schema form library, with a theme package for styling.
- **Pros:** Handles the whole specification including nesting, arrays, and conditionals. Battle-tested; no renderer to maintain.
- **Cons:** Substantial dependency plus a theme package, for schemas that are currently flat structs of strings. Its styling is opinionated and its escape hatches (widgets, field templates) are a second abstraction to learn beside our own custom-component slot. Draft-2020-12 support across its themes is uneven.

### Option C — Ship the Effect Schema to the client and generate from the AST
- **Description:** Skip JSON Schema; give the client the actual schema.
- **Pros:** Richest possible information, and the client could reuse the same schema for validation.
- **Cons:** An Effect Schema is code, not data — it cannot cross a wire without shipping the pack's modules to the browser, which breaks the boundary the catalog exists to provide. Rejected on architecture, not effort.

## Evaluation criteria
1. Fit with the schemas actually published today
2. Dependency weight and styling control in a console we want to iterate on
3. Graceful behaviour on a schema the renderer does not understand
4. Preserves the §4.1 principle: generated by default, custom on demand
5. Cost to change if schemas grow complex

## Analysis
- **Criterion 1 is where B loses.** `@rjsf` is priced for arbitrary user-authored schemas; ours are generated from `Schema.Struct`s with primitive fields. Paying a large dependency and a theme layer to render three text inputs is poor value, and the styling fight is real in a console we expect to iterate on visually (criterion 2).
- **Criterion 3 is the safety argument for A.** The failure mode of a hand-built renderer is a shape it does not recognise; with a raw-JSON fallback that becomes "less convenient" rather than "broken", and the operator can still run the transform. That fallback is cheap and makes A's coverage gap survivable.
- **Criterion 4 is satisfied by both**, but A composes more simply: one custom-component registry, not a registry plus a widget/template system.
- **Criterion 5 is A's genuine risk.** If packs start publishing nested or conditional schemas, A's renderer grows or B becomes right. That is a real possibility — geolocation and chronolocation inputs in `04-web-ui.md` §4.1 are exactly the shapes that get complicated — but those are named there as *custom component* cases anyway, which is the escape hatch rather than the generator's job.
- C is disqualified: shipping pack modules to the browser dissolves the catalog boundary.

## Recommendation
- **Option A.** A small renderer in the console over the JSON Schema the catalog already publishes: primitives, enums, required/optional, descriptions as help text, and a raw-JSON fallback for anything else. Per-transform custom components register by transform id and take precedence.
- Client-side validation is convenience only; the engine's boundary decode remains authoritative (I6), and the console surfaces its errors rather than pre-empting them.
- **What would change this decision:** packs publishing nested, array-heavy, or conditional inputs often enough that the fallback becomes the common path — at which point adopting `@rjsf` behind the same custom-component seam is a contained swap, because the renderer is called in exactly one place.

## Open questions
- Whether output schemas get a symmetric generated *view* or stay a JSON/table dump initially. Deferred: it changes no contract and no requirement, only the results pane.
